notile-unrolljam-nonpermutable

Loop jamming crossed a permutable-band boundary

What This Case Checks

Replays an optimizer proposal or hint that PolCert cannot certify.

Expected outcome
The route must reject or replace the uncertifiable effect described here: Under --notile, candidate discovery assumes one tiled level and crosses the real permutable-band boundary, jamming a dependence-carrying loop.
Recorded outcome
Proved block unrolling is retained, but the unsafe local jam is refused.
Why this test matters
These cases demonstrate that optimizer output is evidence to check, not a trusted correctness claim.

Original C Program

#include <stdio.h>

#define I 2
#define H 2
#define J 6
#define K 6

static int a[I][H][J][K];
static int b[I][H][K];

int main(void) {
  int i, h, j, k;

  for (i = 0; i < I; i++) {
    for (h = 0; h < H; h++) {
      a[i][h][0][3] = 10;
      for (k = 0; k < K; k++)
        b[i][h][k] = k + 1;
    }
  }

#pragma scop
  for (i = 0; i < I; i++)
    for (h = 0; h < H; h++)
      for (j = 1; j < J; j++)
        for (k = 0; k < K; k++)
          a[i][h][j][k] = a[i][h][j - 1][3] + b[i][h][k];
#pragma endscop

  printf("%d\n", a[0][0][2][0]);
  return 0;
}

Why Rejection Is Correct

Classification
Confirmed official Pluto unroll-and-jam miscompilation
Reason
Jamming crosses a dependence-carrying loop, so one copied body reads a value before the neighboring copied body writes it.
Optimizer behavior
With --notile, Pluto still assumes one tiled level and skips the real permutable-band boundary when choosing the jam loop.
Correctness consequence
The generated adjacent j bodies violate the inner-k dependence; the recorded result changes from 15 to 1.
PolCert response
PolCert retains proved block unrolling but its local affine check refuses the unsafe jam.
